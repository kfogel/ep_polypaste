● Yes, this is doable with a small client-side Etherpad plugin, and I think it's
  the right approach. Copy-paste doesn't need to change anything on the server.
  Your admin access matters only because you'll have to install the plugin.

  Why copying loses the nesting now

  Etherpad doesn't store a nested list as nested HTML. Each line of the pad is
  its own <div>, and a list item at any depth looks roughly like this:

  <div><ul class="list-bullet3"><li>third-level item</li></ul></div>

  The depth exists only in the class name (list-bullet1, list-bullet2, …, or
  list-numberN, or list-indentN for indentation without bullets). CSS turns that
  class into visual indentation. When Firefox builds the clipboard's plain
  text, it sees a flat run of one-item lists all at the same depth, so the
  indentation disappears. Any browser would do the same, and GNOME and Wayland
  aren't the cause.

  The fix: take over the copy event

  The editor text lives in a nested iframe (ace_outer → ace_inner). A plugin can
  use Etherpad's postAceInit client hook to attach a copy listener to that
  inner document. The listener would:

  1. Get the current selection and find the line <div>s it covers.
  2. Read each line's list type and level from the list-(bullet|number|indent)N
     class, and take just the selected part of its text. The first and last
     lines may be only partly selected.
  3. Put your own content on the clipboard:
     - text/plain: each line prefixed by N−1 TABs, optionally followed by a
       marker such as -  or 1. .
     - text/html: a properly nested <ul>/<ol> version of the same selection.
       Pasting into LibreOffice, Google Docs, email clients and so on would then
       keep real nested lists as well.
  4. Call event.preventDefault() so the browser uses your version instead of its
     own.

  That's about 100–150 lines of JavaScript plus the standard ep.json and
  package.json. It needs no server-side code.

  Limits and details

  - Middle-click paste won't be covered. On Linux, the "primary selection"
    (select, then middle-click) doesn't fire a copy event, so no page can change
    what it holds. Only Ctrl+C (and the right-click Copy menu item) would carry
    the tabs. This is a browser limitation.
  - Cut (Ctrl+X) takes more work. In a cut handler, the browser only uses your
    clipboard data if you call preventDefault(), and that also stops the text
    from being deleted. The plugin would then have to delete the selection
    through Etherpad's editor API so the change syncs to other users. It's
    feasible but fiddlier, so I'd do copy first and add cut afterwards.
  - Pasting back into Etherpad: Etherpad's paste handler would receive the
    nested HTML. I expect it to rebuild the list levels, but that needs testing.
  - Output format: TABs are easy to make configurable. Since this directory is
    named ep_org_export, you may want org-mode style instead (for example - 
    bullets with spaces for indentation, or * headings by depth). The same code
    could produce any of these.

  If you'd like, I can write the plugin here in ~/src/ep_org_export. It would be

  2.x (or through the admin UI once it's published). Tell me which plain-text
  format you want: plain TABs only, TABs plus bullet or number markers, or
  org-mode style.

● No, a user sets it once per browser, not once per pad. The plugin stores the
  choice in the browser's localStorage, which the browser keys by site
  (https://pad.opentechstrategies.com), not by page. Every pad on your server,
  in that browser, shares the setting.

  So it's the second kind of memory you described, limited to one server:

  - Remembered: all pads on pad.opentechstrategies.com, in the same browser
    profile, including after restarting the browser.
  - Not carried over:
    - to a different browser or computer;
    - to private windows;
    - to a different Etherpad server;
    - after the user clears that site's data.

  The only server-side part is the default for people who haven't chosen yet,
  set by you in settings.json. That applies to every user on the server.

  True per-person memory on the server, following someone across browsers and
  machines, would need Etherpad to know who the person is. By default it
  doesn't. It only knows an "author" identity, which is itself a cookie in that
  browser, so storing the setting under it would gain nothing over the current
  approach. It becomes worthwhile if your server uses login (Etherpad 3.x
  supports single sign-on). Then the plugin could save the choice under the
  logged-in user's name. That would take a few more hooks and a small database
  entry per user. Tell me if you use login and want that.
