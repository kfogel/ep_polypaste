● Yes, this is doable with a small client-side Etherpad plugin, and I think it's
  the right approach. Copy-paste doesn't need to change anything on the server.
  Your admin access matters only because you'll have to install the plugin.

  Why copying loses the nesting now

  Etherpad doesn't store a nested list as nested HTML. Each line of the pad is
  its own <div>, and a list item at any depth looks roughly like this:

  <div><ul class="list-bullet3"><li>third-level item</li></ul></div>

  The depth exists only in the class name (list-bullet1, list-bullet2, …, or
  list-numberN, or list-indentN for indentation without bullets). CSS turns that
  class into visual indentation. When Firefox builds the clipboard's plain
  text, it sees a flat run of one-item lists all at the same depth, so the
  indentation disappears. Any browser would do the same, and GNOME and Wayland
  aren't the cause.

  The fix: take over the copy event

  The editor text lives in a nested iframe (ace_outer → ace_inner). A plugin can
  use Etherpad's postAceInit client hook to attach a copy listener to that
  inner document. The listener would:

  1. Get the current selection and find the line <div>s it covers.
  2. Read each line's list type and level from the list-(bullet|number|indent)N
     class, and take just the selected part of its text. The first and last
     lines may be only partly selected.
  3. Put your own content on the clipboard:
     - text/plain: each line prefixed by N−1 TABs, optionally followed by a
       marker such as -  or 1. .
     - text/html: a properly nested <ul>/<ol> version of the same selection.
       Pasting into LibreOffice, Google Docs, email clients and so on would then
       keep real nested lists as well.
  4. Call event.preventDefault() so the browser uses your version instead of its
     own.

  That's about 100–150 lines of JavaScript plus the standard ep.json and
  package.json. It needs no server-side code.

  Limits and details

  - Middle-click paste won't be covered. On Linux, the "primary selection"
    (select, then middle-click) doesn't fire a copy event, so no page can change
    what it holds. Only Ctrl+C (and the right-click Copy menu item) would carry
    the tabs. This is a browser limitation.
  - Cut (Ctrl+X) takes more work. In a cut handler, the browser only uses your
    clipboard data if you call preventDefault(), and that also stops the text
    from being deleted. The plugin would then have to delete the selection
    through Etherpad's editor API so the change syncs to other users. It's
    feasible but fiddlier, so I'd do copy first and add cut afterwards.
  - Pasting back into Etherpad: Etherpad's paste handler would receive the
    nested HTML. I expect it to rebuild the list levels, but that needs testing.
  - Output format: TABs are easy to make configurable. Since this directory is
    named ep_org_export, you may want org-mode style instead (for example - 
    bullets with spaces for indentation, or * headings by depth). The same code
    could produce any of these.

  If you'd like, I can write the plugin here in ~/src/ep_org_export. It would be
  installable with pnpm run plugins i --path /path/to/ep_org_export on Etherpad
  2.x (or through the admin UI once it's published). Tell me which plain-text
  format you want: plain TABs only, TABs plus bullet or number markers, or
  org-mode style.

  machines, would need Etherpad to know who the person is. By default it
  doesn't. It only knows an "author" identity, which is itself a cookie in that
  browser, so storing the setting under it would gain nothing over the current

  one does Etherpad actually load at startup time?  If I want to uninstall a

● Startup also reads var/installed_plugins.json and reinstalls everything listed
  there, which matters for uninstalling. I'll check how plugins are found at

  Ran 2 shell commands (ctrl+o to expand)
● src/plugin_packages/PLUGIN_NAME holds the plugin's actual files, and
  src/node_modules/PLUGIN_NAME is normally just a symlink to that directory. So
  both paths lead to the same files, and those are what Etherpad loads. To
  uninstall, use Etherpad's own command, which removes both and also updates a
  list you'd otherwise miss. This is from reading Etherpad's current develop
  source, mainly src/static/js/pluginfw/installer.ts and LinkInstaller.ts. If
  your server runs an older release, check that it behaves the same.

  src/plugin_packages/PLUGIN_NAME
  - This is the real installed copy. Etherpad's plugin installer (the
    live-plugin-manager library) puts it there.
  - With plugins i --path, it's a copy of your source directory as it was when
    you installed.
  - It's kept outside node_modules so that upgrading Etherpad doesn't wipe
    installed plugins.

  src/node_modules/PLUGIN_NAME
  - This is normally a symlink to src/plugin_packages/PLUGIN_NAME.
  - It exists so ordinary Node module loading works. The hook paths in ep.json
    (like ep_polypaste/index:...) and the plugin's own require() calls resolve
    through node_modules.

  Which one is loaded: in effect, plugin_packages. The list of installed plugins
  comes from the plugin installer, which reads plugin_packages. The code is
  loaded through the node_modules symlink, so it's the same files.

  What happens at startup:
  - Missing symlinks get recreated. Etherpad scans src/plugin_packages/ and
    creates a src/node_modules/ symlink for any plugin that lacks one.
  - Listed plugins get reinstalled. Etherpad reads var/installed_plugins.json
    and reinstalls every plugin listed there.

  That's why there are really three things to clean up, not two.

  To uninstall, use Etherpad's command rather than deleting directories:

  pnpm run plugins rm PLUGIN_NAME

  It removes the node_modules symlink, deletes the plugin_packages directory,
  removes any dependencies no other plugin needs, and rewrites
  var/installed_plugins.json.

  If you delete things by hand, remove all three:
  1. src/node_modules/PLUGIN_NAME (the symlink)
  2. src/plugin_packages/PLUGIN_NAME
  3. The plugin's entry in var/installed_plugins.json

  If you remove only some of them:
  - Only the symlink: it comes back at the next startup.
  - Only plugin_packages: you leave a broken symlink.
  - Either or both, but not the installed_plugins.json entry: Etherpad tries to
    reinstall the plugin at startup. For a plugin installed from a local path
    that isn't on npm, that probably just logs an error. For an npm-published
    plugin, it would quietly come back.

  This also explains the earlier ep_org_export duplicate. Installing under the
  new name added a second entry rather than replacing the old one, so both
  plugins were loaded until you removed the old one.

  other than none takes on some layout roles, even an identity transform like
  scale(1). The relevant one here: it becomes the reference box for all its
  position: fixed descendants. Normally a fixed element is positioned relative
  to the browser window. Inside a transformed ancestor, it's positioned relative
  to that ancestor instead. This is standard, specified behaviour; filter,
  perspective and will-change: transform have the same effect.

  Why that breaks the menus. The dropdown lists are position: fixed so they can
  float outside the popup's scroll area. When a list opens, Etherpad's
  nice-select code measures where the menu button is on screen, relative to the
  window, and writes those numbers into the list's left and top. The browser
  then measures them from the panel's top-left corner instead of the window's.
  The panel's own distance from the window's corner gets counted twice, and the
  list lands that far down and to the right. On your pad that pushed it to about
  x=2123 in a 1,400-pixel-wide window, off-screen and clipped by the panel.

  What the new value does. transform: none means no transform at all, so the
  panel is no longer the reference box. The window is again, which is what
  nice-select's arithmetic assumes. It looks exactly the same as scale(1),
  because scale(1) never changed the appearance anyway.

  Why I'm confident it's right:
  - It matches the normal case. With no motion preference, the panel's transform
    is already none; my headless test showed it. That's the configuration
    everyone without reduced motion uses, where the menus work. The fix just
    gives reduced-motion users the same value everyone else already has.
  - I tested it. With the override injected and reduced motion emulated, the
    Font type list opened at exactly the same place as the no-preference run
    (left: 1136, top: 450).
  - It keeps what the rule is for. The rule exists to switch off animation for
    people who asked for less motion. The transition: none beside it still does
    that, and the fix leaves it alone.

  Caveats a reviewer might raise:
  - Layering. A non-none transform also puts the element in its own drawing
    layer (a "stacking context"), which affects how z-index layering works.
    Removing it could in principle change what draws on top of what. In
    practice, the popup around the panel almost certainly creates its own layer
    already, and the panel already runs without one for users without reduced
    motion. I haven't checked the popup's CSS to confirm, though.
  - A sturdier alternative. The fix removes the trigger, not the fragility.
    nice-select still assumes nothing between the list and the window has a
    transform. A future style or plugin that puts a transform or filter on the
    popup would break the menus again. A more thorough fix would make
    nice-select account for such an ancestor when positioning the list. That's a
    bigger change and harder to review, so I'd propose the one-liner and
    perhaps mention this as a follow-up in the issue.
  - Animation. The popup's opening zoom (scale(0.7) with a transition) is set on
    the outer .popup element, which this rule doesn't touch. As far as I can
    tell, reduced-motion users still see that zoom both before and after the
    fix. It's a separate issue, and the fix neither causes nor cures it.

  Why recovery is possible without a backup: Etherpad's dirty database (the
  dirty-ts library, via ueberdb2) only ever appends to var/dirty.db. Each change
  is one line of JSON, and a deletion is just another line with no value, like
  {"key":"pad:test-polypaste"}. The file is never compacted, so the pads' data
  is probably still there, before the deletion lines the test wrote. Recovering
  means cutting the file off just before those deletions.

  Run all commands from the top of the Etherpad tree.

  Option A: you have a backup copy of dirty.db

  1. Stop Etherpad. For example sudo systemctl stop etherpad, or however you run
     it. Etherpad reads the whole file into memory at startup and keeps
     appending to it, so it must not be running while you swap files.

     cluster. The deletions run in parallel, so they aren't in alphabetical

● Not quite. The format that matters is the HTML copy the plugin puts on the
  clipboard for rich-text apps, not the "HTML source" choice in the menu.

  There are two separate HTML outputs. Each copy puts two versions on the
  clipboard (static/js/index.js, lines 97–98):
  - text/plain: whatever format the user picked in Settings. "HTML source" is
    one of those choices; it's HTML as plain text, for pasting into a text
    editor.
  - text/html: always produced by renderClipboardHtml(), whatever the Settings
    choice. Rich-text apps paste this version, and that includes another
    Etherpad pad.

  So pasting between pads always uses renderClipboardHtml(), and that's the
  output that would have to keep the zero-width spaces.

  The current structure doesn't allow that. The padding is stripped in
  lineModel(), before any output is produced, so nothing downstream ever sees
  it. To keep it for one output, the model would have to keep the padding
  characters, perhaps marked as padding. Then every text format would drop them,
  and renderClipboardHtml() alone would keep them. It's a modest change.

  There are reasons to hesitate:
  - Every rich-text app would get them too. The plugin can't tell where you'll
    paste, so Word, Gmail, LibreOffice and the rest would all receive the
    zero-width spaces, which is what you wanted to avoid.
  - It may not work anyway. I haven't checked whether Etherpad keeps a
    zero-width space when it pastes HTML, or whether ep_hyperlinked_text would
    treat the pasted characters as its padding. That would need testing in a
    real pad before it's worth doing.

  I'd leave it as it is unless losing the padding in the destination pad turns
  out to be a real annoyance.
